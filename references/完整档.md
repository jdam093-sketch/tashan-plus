# 完整档：详细做法

完整档用于：法律结论、要公开发布、要做成长期提示词或技能、快速档说不清的题。
保留原版他山的十步，加上"先写已知""样本核实分级""成品检验""预估与上限"。

---

## 〇、开工前：先报预估，等"开始"

先给用户发一份预估（和第 1 步定边界合并成一次停顿）：

```markdown
【完整档预估】
主题：……
我理解的目标：……　本轮不做：……　最终沉淀物：……
步骤：共 N 步（列出）
样本：计划 X 个（默认 ≤10）
大约用时：X 分钟（默认 30–60 分钟；估计）
成品检验：出 2–3 道题，打分方式：另一个模型打分 / 自测（标"未独立验证"）
外部模型打分：用 / 不用；用哪家：……
预计费用：订阅额度内的不单独计费；按量付费的 API 预计 ¥X（估计，不确定）
需要您确认的：……
您回"开始"我再动手。
```

**默认范围**：30–60 分钟；样本 ≤10 个；成品检验一轮。

**中途停下请示的情况（任一出现就停）**：

- 预计 API 费用超过 ¥30；
- 实际用时超过 90 分钟；
- 样本要超过 15 个；
- 订阅额度不足，或出现额度快用完的提示。

计划内停顿共 2 次（预估、骨架确认）；隐私、超限、法律判断冲突是例外停顿，不计次数。

停下时说明：做到哪一步、已产出哪些文件、继续还要多少时间和费用。已写出的内容先保存。

开工前没人可问（命令行自动跑、机器人代跑）时，不开完整档，改走快速档，并在汇报里写"建议升完整档，待确认"。

## 1. 定边界

明确：这次是学习、审核、对标，还是马上执行？真正的主问题是什么？本轮不做哪些事（不安装依赖、不配置 API、不启动服务、不改主工程）？结果沉淀成什么（样本索引、学习笔记、决策备忘、提示词草案、技能草案、SOP）？

用户已明确"先学习"时，不擅自进入搭建或执行。

## 2. 先写已知（一页）

写下本来就知道的：这个领域的常见做法、主要概念、自己的判断。最后对照，填完整笔记里的「这次学到的新东西（推翻 / 加深 / 新增）」。写好先存盘，再开始找样本；用户随请求给了样本的，先只看请求部分。已先看过样本的，标「事后补记」。

## 3. 找样本

围绕同一问题找参照物，默认不超过 10 个：

- 官方文档或官方仓库；
- 高质量开源仓库；
- 相邻领域的优秀技能；
- 行业工具或产品案例；
- 反面样本或常见失败做法。

在用户授权范围内补样本；信息可能过期时应联网核对，但用户禁止联网或限制资料范围时遵守限制并标局限，不自行扩大范围。实际样本超过预估（包括 11–15 个）时，在汇报说明数量与理由；超过 15 个前仍停下请示。搜索词遵守 `references/隐私规则.md`。

## 4. 建索引并核实分级

索引至少记录：名称、来源链接、本地路径（如已拉取）、当前版本或提交/发布日期、它解决的问题、适合学习的层级、不适合迁移的部分、**核验日期、等级**。

等级（通用）：

- **A 已核实**：打开了原文/官方页面，内容对得上；
- **B 二手**：只看到转述、摘要；
- **C 未核实**：没打开、打不开、离线未核验的网上来源、只凭印象。

**没有真正打开过的样本，不能用来下结论。** 离线未核验的网上来源标 C；真正打开过的本地原件按实际情况定 A/B/C，注明“本地副本，版本 / 日期为……”，未知就写未知；A 只证明该副本内容，不证明最新状态。法规仍须按领域模板核验，不放宽。A 可独立支持对应结论，B 须标“据转述”，C 仅作线索。

不同领域的"好坏"标准另定：仓库可看维护是否活跃、是否官方；法规看效力层级和是否现行有效（见 `templates/领域-法律合规.md`）；账号看是不是平台官方、头部还是普通。

索引的价值是让以后能继续学，不用重新搜索。

## 5. 拆对象模型（最重要）

不要只问"它有哪些功能"，要问：

- 它把复杂任务拆成了哪些对象？
- 输入是什么？中间产物是什么？最终输出是什么？
- 哪些对象是为了让 AI 更容易处理？哪些是为了让人更容易审核？

例子：

- 视频剪辑：逐词时间戳、剪辑边界、字幕文件、包装层、审核清单。
- 写作系统：立意、素材、结构、场景、草稿、审稿、发布。
- 投研系统：假设、证据、反证、估值、风险、决策记录。

对象模型比命令更重要，它决定了后续提示词的骨架。

## 6. 拆工作协议

谁先判断？谁执行？谁审核？哪里需要人确认？什么情况打回？什么情况继续？失败时保留什么证据？用户反馈如何沉淀？

好技能一定有工作协议；差提示词往往只有角色扮演。

## 7. 拆质量门

- 前置判断门：是否先确认目标、策略、输入。
- 执行过程门：是否有中间产物可检查。
- 交付检查门：是否有规格、边界、安全、完整性检查。
- 独立审核门：是否由不同角色复查。
- 进化门：是否把错误写回规则。

没有质量门的提示词，只是一次性回答，不是能长期协作的系统。

## 8. 拆隐含世界观

它认为这个领域最大的难点是什么？默认机器擅长什么、不擅长什么？让人参与哪类判断？把什么视为"好结果"？牺牲了什么来换稳定？

这一步决定我们是整体吸收，还是只借鉴局部。

## 9. 横向对照，提炼不可变原则

把所有样本放进同一张表：切法有何不同、哪些共识反复出现、哪些设计互相冲突、哪些只是工程实现、哪些是可迁移原则、哪些适合现在、哪些以后再说。

不要把工具分成"好/坏"，要分成"适合哪一层"。

不可变原则要能指导行动，例如：

- 先内容，后包装。
- 字幕必须基于剪后音频。
- 主执行者不能自己给自己最终放行。
- 用户反馈要整合进正文规则，而不是只放日志。
- 生成素材服务表达，不能替代表达。

不写空话，比如"提高质量""优化体验"。

## 10. 形成我们自己的工作协议，再写草案

先列骨架：任务边界、输入规范、判断顺序、中间产物、人机分工、质量门槛、失败处理、反例清单、进化机制。

**第二次停下**：把骨架给用户确认。此时已获准开工；若联系不上用户，可按骨架继续写草案，标“骨架未确认”，只在已批准的范围和预算内继续，不追加费用，不另开第二轮检验；触及四条停止条件仍须停下。这不等于允许开工前无确认就进入完整档。

确认后（或符合上述失联兜底时），用 `templates/提示词骨架.md` 写出提示词、SOP 或技能草案。

---

## 11. 成品检验（一轮）

目的：检验这次做出来的草案好不好用（不是检验本技能）。

1. 出 2–3 道贴近用户实际用途的题。
2. 用草案做一遍，再不用草案做一遍（或与用户原来的做法对比）。
3. 打分：
   - 最好由另一个模型打分（订阅内的另一家助手，或预估里写明的按量付费 API）；
   - 做不到就自测，并在检验记录里写明「未独立验证」。
4. 交给外部模型的题目和材料同样遵守隐私规则：只给脱敏后的、公开类别的内容。
5. 记录：题目、两种做法的结果摘要、打分方式、得分、发现的问题、改了什么。

只打一轮。要第二轮，先问用户。

## 12. 失败处理

上不了网、样本不足 3 个、链接打不开、资料互相矛盾时：如实写明，降低结论的确定程度，列出"要核实的事"。宁交标清局限的 60 分，不交编出来的 90 分。

## 完整档产出

1. 样本索引（可并入完整笔记第三节）；
2. 完整取经笔记（`templates/完整笔记.md`）；
3. 提示词 / SOP / 技能草案（`templates/提示词骨架.md`）；
4. 成品检验记录（可并入完整笔记第十节）。

都按当前项目规则放到当次任务输出目录；无任务文件夹时按 `SKILL.md` 第八节兜底。
